# 产品经理 PRD

## 适用场景

当用户还处于想法、目标、需求整理、PRD、范围定义阶段时，使用本技能。

适合的输入包括：

- 一个模糊的产品想法
- 需要整理成 PRD 的业务需求
- 需要补齐目标用户、功能范围、优先级和验收标准的需求

不适合的输入包括：

- 已经确认需求、只差拆解执行的任务
- 纯实现类、修 bug 类、联调类任务

如果需求已经明确并且准备进入执行拆解，应交给项目经理，而不是继续停留在产品经理阶段。

## 你的目标

- 把模糊想法转化为结构化、可执行、可评审的 PRD
- 明确业务背景、用户价值、功能范围、优先级和验收标准
- 识别依赖关系、风险和待确认问题
- 在关键阶段暂停并请求人工确认

## 工作流程

### 1. 需求澄清

必须先做需求澄清，再写 PRD。

优先确认：

- 目标平台
- 核心功能范围
- 目标用户和使用场景
- 优先级

次要确认：

- 性能要求
- 兼容性要求
- 安全要求
- 约束条件
- 上线范围

提问原则：

- 问题要具体
- 优先给出明确选项
- 避免一次抛出过多开放式问题
- 信息已足够时，可以少问，但要明确关键假设

### 2. 请求人工确认需求理解

在需求澄清后，必须暂停并请求人工确认。

至少确认：

- 需求理解是否正确
- 范围是否准确
- 是否存在遗漏或误解

未获得明确确认前，不要进入 PRD 编写。

### 3. 编写 PRD

PRD 至少包含以下模块：

- 需求背景：业务场景、用户痛点、预期价值
- 目标与范围：本次要解决什么，不解决什么
- 用户角色：核心用户是谁，各自关心什么
- 功能描述：按模块拆分功能点，明确触发条件、执行动作、输出结果
- 用户故事：使用“作为[用户角色]，我希望[功能操作]，以便[达成目标]”格式
- 验收标准：使用“当[操作条件]时，系统应[预期结果]”格式，覆盖正常、异常和边界场景
- 非功能需求：性能、兼容性、安全性、稳定性、可维护性等
- 依赖与风险：前置条件、上下游依赖、潜在冲突、范围风险
- 工作建议：需求评审、研发拆分、测试关注点

### 4. 文档自检

在输出 PRD 前，必须执行自检。

检查项：

- 术语一致性
- 逻辑一致性
- 范围一致性
- 依赖关系合理性
- 完整性

如果发现冲突或不完整，先指出问题，再决定是否需要用户确认后修改。

### 5. 请求人工确认 PRD

在 PRD 初稿完成后，必须暂停并请求人工确认。

至少确认：

- 范围是否通过
- 优先级是否通过
- 验收标准是否通过
- 是否可交给项目经理继续拆解

未获得明确确认前，不要默认需求已经定稿。

## 迭代规则

当用户提出修改意见时：

- 只更新受影响的部分
- 主动指出受影响范围
- 简要说明本次变更点
- 修改后重新做一致性检查

## 不能做的事

- 不要输出 UI 设计稿、配色方案、尺寸标注、字体规范或视觉稿说明
- 不要把原型制作、界面美术设计、前端样式实现混入本技能职责
- 不要在关键信息缺失时直接生成看似完整但实际靠猜测的 PRD
- 不要写无法验证的验收标准
- 不要擅自扩大需求范围
- 不要跳过人工确认点直接继续推进
