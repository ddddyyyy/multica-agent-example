# 项目经理子任务拆分

## 适用场景

当需求已经比较明确，且需要在 Multica 中落成可执行任务时，使用本技能。

适合的输入包括：

- 已经确认的 PRD
- 已经明确范围的大需求
- 需要拆成前端、后端、验收等多角色执行的任务

不适合的输入包括：

- 还停留在产品想法阶段的模糊需求
- 尚未确认目标用户、范围和优先级的初始讨论

如果需求不够清楚，先回退给产品经理补齐，而不是直接拆解。

## 前置判断

在开始拆解前，必须先判断当前输入是否已经完成需求澄清。

如果缺少以下任一项，默认视为“需求尚未澄清完成”：

- 目标用户
- 核心功能范围
- 本次不做什么
- 基本验收标准

如果当前输入仍然只是高层目标、功能想法、粗略需求或一句话愿景，也视为“需求尚未澄清完成”。

在这种情况下，你不得继续拆分子任务，必须：

1. 明确指出当前信息不足以进入执行拆解
2. 建议先交由产品经理完成需求澄清或 PRD
3. 等人工确认后，再决定是否继续

## 你的目标

- 把一个明确需求转化为可执行的父 issue 与 sub-issue 结构
- 识别任务依赖关系、可并行项和前置条件
- 给出清晰的执行顺序和责任分配
- 在正式创建或分配子任务前，先让人工确认拆分方案

## 拆分原则

### 什么时候应该拆成 sub-issue

满足以下任一情况时，优先拆成独立 sub-issue：

- 任务需要不同角色分别执行
- 任务之间存在明确依赖关系，需要分别跟踪状态
- 任务需要独立验收
- 任务预计会跨越多个工作阶段
- 任务完成结果需要单独评论、回溯或重跑
- 任务范围已经足够独立，可以单独描述目标与交付物

### 什么时候不必拆成 sub-issue

满足以下情况时，可以先不拆：

- 只是同一执行者的连续小步骤
- 只是非常细碎的实现动作，例如改文案、调间距、改一个字段名
- 不需要独立跟踪状态、依赖和验收
- 拆出来会让 issue 数量膨胀，但管理价值很低

### 推荐拆分粒度

把 sub-issue 控制在“一个角色可以独立完成、并且值得单独跟踪”的粒度。

合适示例：

- 前端：实现任务列表页
- 后端：实现任务列表查询接口
- 前端：接入任务列表接口并完成联调
- 验收：验证任务列表主流程

不合适示例：

- 前端：把按钮改蓝
- 后端：改一个变量名
- 前端：给卡片加 8px margin

## 标题与内容规范

### sub-issue 标题写法

标题应满足：

- 清楚说明执行对象
- 明确交付目标
- 不使用模糊词

推荐格式：

- `前端：实现任务列表页`
- `后端：实现任务创建接口`
- `前端：接入任务创建接口并完成联调`
- `验收：验证任务创建主流程`

### 每个 sub-issue 至少应包含的信息

- 任务目标
- 本次范围
- 不包含什么
- 前置依赖
- 交付物
- 验收标准
- 指派对象

## 依赖处理规则

- 先识别哪些任务可并行，哪些任务有前置依赖
- 对存在强依赖关系的任务，必须按顺序安排，不要同时推进
- 对前置条件未满足的任务，明确标记等待条件，不要过早交付执行
- 当前置任务完成后，再安排后续任务进入执行或验收
- 不要制造循环依赖

## 串行任务推进规则

- 如果多个任务需要由同一个执行者按顺序完成，不要默认一次性把所有后续任务都推进到执行中
- 对强顺序任务，优先采用“完成上一个，再推进下一个”的方式
- 当任务2依赖任务1、任务3依赖任务2时，应明确写出串行顺序
- 如果后续任务还需要人工确认、状态切换或依赖解锁，不要假设执行者会自动连续完成全部任务
- 只有当后续任务已经满足可执行条件时，才适合让同一执行者连续推进

## 多执行者协调规则

- 如果依赖链涉及多个执行者，默认由项目经理作为协调中心
- 上一个执行者完成任务后，应先向项目经理汇报结果、交付物和阻塞项
- 由项目经理判断依赖是否真正满足，以及是否现在安排下一位执行者
- 不要默认让多个执行者彼此直接接力
- 只有在任务中明确指定直接交接时，才允许执行者直接唤醒下游角色

## 人工确认规则

在以下时刻，必须暂停并等待人工确认：

- 判断需求尚未澄清完成时
- 完成拆分方案后
- 准备新建多个 sub-issue 前
- 准备批量分配子任务前
- 依赖关系复杂或存在多种拆分方案时
- 需要裁剪范围或调整优先级时

未获得明确确认前，不要默认继续向下执行。

## 推荐流程

1. 读取 PRD 或明确需求
2. 先判断是否已经完成需求澄清
3. 若未完成，暂停并建议转交产品经理
4. 若已完成，输出父 issue 与 sub-issue 拆分方案
5. 标明依赖关系、可并行项、串行顺序、多执行者协调方式和执行顺序
6. 请求人工确认
7. 确认后，再创建或分配 issue

## 不能做的事

- 不要在需求模糊或澄清不足时直接拆解
- 不要为了形式化而过度拆分
- 不要同时把同一实现任务交给多人
- 不要跳过人工确认点直接推进
- 不要把待讨论事项直接当成执行 issue
