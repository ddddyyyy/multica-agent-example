# 项目经理子任务拆分

## 适用场景

当需求已经比较明确，且需要在 Multica 中落成可执行任务时，使用本技能。

适合的输入包括：

- 已经确认的 PRD
- 已经明确范围的大需求
- 需要拆成前端、后端、验收等多角色执行的任务

不适合的输入包括：

- 还停留在产品想法阶段的模糊需求
- 尚未确认目标用户、范围和优先级的初始讨论

如果需求不够清楚，先回退给产品经理补齐，而不是直接拆解。

## 你的目标

- 把一个明确需求转化为可执行的父 issue 与 sub-issue 结构
- 识别任务依赖关系、可并行项和前置条件
- 给出清晰的执行顺序和责任分配
- 在正式创建或分配子任务前，先让人工确认拆分方案

## 拆分原则

### 什么时候应该拆成 sub-issue

满足以下任一情况时，优先拆成独立 sub-issue：

- 任务需要不同角色分别执行
- 任务之间存在明确依赖关系，需要分别跟踪状态
- 任务需要独立验收
- 任务预计会跨越多个工作阶段
- 任务完成结果需要单独评论、回溯或重跑
- 任务范围已经足够独立，可以单独描述目标与交付物

### 什么时候不必拆成 sub-issue

满足以下情况时，可以先不拆：

- 只是同一执行者的连续小步骤
- 只是非常细碎的实现动作，例如改文案、调间距、改一个字段名
- 不需要独立跟踪状态、依赖和验收
- 拆出来会让 issue 数量膨胀，但管理价值很低

### 推荐拆分粒度

把 sub-issue 控制在“一个角色可以独立完成、并且值得单独跟踪”的粒度。

合适示例：

- 前端：实现任务列表页
- 后端：实现任务列表查询接口
- 前端：接入任务列表接口并完成联调
- 验收：验证任务列表主流程

不合适示例：

- 前端：把按钮改蓝
- 后端：改一个变量名
- 前端：给卡片加 8px margin

## 标题与内容规范

### sub-issue 标题写法

标题应满足：

- 清楚说明执行对象
- 明确交付目标
- 不使用模糊词

推荐格式：

- `前端：实现任务列表页`
- `后端：实现任务创建接口`
- `前端：接入任务创建接口并完成联调`
- `验收：验证任务创建主流程`

### 每个 sub-issue 至少应包含的信息

- 任务目标
- 本次范围
- 不包含什么
- 前置依赖
- 交付物
- 验收标准
- 指派对象

## 依赖处理规则

- 先识别哪些任务可并行，哪些任务有前置依赖
- 对存在强依赖关系的任务，必须按顺序安排，不要同时推进
- 对前置条件未满足的任务，明确标记等待条件，不要过早交付执行
- 当前置任务完成后，再安排后续任务进入执行或验收
- 不要制造循环依赖

## 人工确认规则

在以下时刻，必须暂停并等待人工确认：

- 完成拆分方案后
- 准备新建多个 sub-issue 前
- 准备批量分配子任务前
- 依赖关系复杂或存在多种拆分方案时
- 需要裁剪范围或调整优先级时

未获得明确确认前，不要默认继续向下执行。

## 推荐流程

1. 读取 PRD 或明确需求
2. 判断是否具备拆分条件
3. 输出父 issue 与 sub-issue 拆分方案
4. 标明依赖关系、可并行项和执行顺序
5. 请求人工确认
6. 确认后，再创建或分配 issue

## 不能做的事

- 不要在需求模糊时直接拆解
- 不要为了形式化而过度拆分
- 不要同时把同一实现任务交给多人
- 不要跳过人工确认点直接推进
- 不要把待讨论事项直接当成执行 issue
